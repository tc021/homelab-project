\section{Overview}

Git was selected as the version control system for the project, while
GitHub is used as the remote repository hosting platform.

Version control is used not only for application source code, but also
for infrastructure configuration, automation scripts, database scripts,
and project documentation.

The repository is intended to act as the central source of truth for
the project and enables development from multiple workstations.

The initial repository structure is designed to support the planned
development of the homelab environment:

\begin{lstlisting}[style=terminal]
homelab-infrastructure/
|
+-- .github/
+-- docs/
|   +-- latex/
|       +-- chapters/
|       +-- images/
|       +-- diagrams/
|       +-- bibliography/
|
+-- infrastructure/
+-- docker/
+-- database/
+-- automation/
+-- ml/
+-- game-servers/
+-- scripts/
+-- .gitignore
+-- README.md
\end{lstlisting}

\section{Git Configuration}

Git was installed and configured on the Ubuntu development environment.

The installed version can be verified using:

\begin{lstlisting}[style=terminal]
git --version
\end{lstlisting}

The global Git configuration contains the identity used for creating
commits.

The configuration can be inspected using:

\begin{lstlisting}[style=terminal]
git config --global --list
\end{lstlisting}

The default branch name for newly initialized repositories was configured
as:

\begin{lstlisting}[style=terminal]
git config --global init.defaultBranch main
\end{lstlisting}

This ensures that newly created repositories use \texttt{main} instead
of the legacy \texttt{master} branch name.


\section{Repository Initialization}

The local project directory was initialized as a Git repository using:

\begin{lstlisting}[style=terminal]
git init
\end{lstlisting}

Git stores repository metadata and history inside the hidden
\texttt{.git} directory.

The repository state can be inspected using:

\begin{lstlisting}[style=terminal]
git status
\end{lstlisting}

The project was subsequently connected to a remote GitHub repository
named \texttt{origin}.

The configured remote repositories can be inspected using:

\begin{lstlisting}[style=terminal]
git remote -v
\end{lstlisting}


\section{SSH Authentication}

SSH key authentication is used for communication between the development
environment and GitHub.

An ED25519 key pair was generated for GitHub authentication.

The SSH configuration associates connections to GitHub with the
dedicated private key:

\begin{lstlisting}[style=terminal]
Host github.com
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_github
    IdentitiesOnly yes
\end{lstlisting}

The private key remains exclusively on the development machine, while
the corresponding public key was registered with the GitHub account.

Connectivity and authentication can be verified using:

\begin{lstlisting}[style=terminal]
ssh -T git@github.com
\end{lstlisting}

During the first connection, the SSH client verifies the host key
presented by GitHub.

The server fingerprint was compared with the fingerprint officially
published by GitHub before the host was added to the local
\texttt{known\_hosts} file.


\section{Default Branch}

The repository was initially created using the legacy
\texttt{master} branch name.

The branch was renamed to \texttt{main} using:

\begin{lstlisting}[style=terminal]
git branch -m master main
\end{lstlisting}

The new branch was subsequently published to the remote repository:

\begin{lstlisting}[style=terminal]
git push -u origin main
\end{lstlisting}

The GitHub repository default branch was changed to \texttt{main}, after
which the obsolete remote \texttt{master} branch was removed.

The repository therefore uses:

\begin{center}
    \texttt{main}
\end{center}

as its primary integration branch.


\section{Branching Strategy}

Direct development on the \texttt{main} branch is avoided.

Each logical change is developed on a dedicated branch created from the
latest version of \texttt{main}.

The general workflow is:

\begin{lstlisting}[style=terminal]
main
 |
 +---- feature / documentation / fix branch
             |
             +---- commits
             |
             +---- push
             |
             +---- Pull Request
                         |
                         +---- review
                         |
                         +---- merge
                                  |
                                  v
                                 main
\end{lstlisting}

\newpage
Branch names describe both the type and purpose of a change.

Examples include:

\begin{lstlisting}[style=terminal]
feature/lab-network-configuration
feature/postgresql
feature/monitoring

docs/initial-documentation
docs/network-verification

fix/virtualbox-host-only-adapter
\end{lstlisting}

The initial project documentation was developed using:

\begin{center}
    \texttt{feature/initial-documentation}
\end{center}

The branch was merged into \texttt{main} after completing the initial
documentation.


\section{Pull Request Workflow}

Changes are integrated into \texttt{main} through Pull Requests.

A typical development cycle consists of:

\begin{enumerate}
    \item synchronizing the local \texttt{main} branch,
    \item creating a dedicated development branch,
    \item implementing and testing the change,
    \item committing the change,
    \item pushing the branch to GitHub,
    \item opening a Pull Request,
    \item reviewing the proposed changes,
    \item merging the Pull Request into \texttt{main},
    \item deleting the completed development branch.
\end{enumerate}

An example workflow is:

\begin{lstlisting}[style=terminal]
git switch main
git pull

git switch -c feature/example-change

# implementation

git add .
git commit -m "feat: implement example change"

git push -u origin feature/example-change
\end{lstlisting}

After the Pull Request is merged, the local repository is synchronized:

\begin{lstlisting}[style=terminal]
git switch main
git pull
git branch -d feature/example-change
\end{lstlisting}

The remote feature branch is also removed after successful integration.


\section{Commit Convention}

Commit messages use a simplified semantic convention inspired by
Conventional Commits.

The currently adopted prefixes include:

\begin{description}
    \item[\texttt{feat:}] introduction of new functionality,
    \item[\texttt{fix:}] correction of an existing problem,
    \item[\texttt{docs:}] documentation changes,
    \item[\texttt{refactor:}] internal changes without introducing
    new functionality,
    \item[\texttt{chore:}] maintenance and repository-related changes.
\end{description}

Example commit messages are:

\begin{lstlisting}[style=terminal]
feat: configure lab host-only network
docs: add network verification tests
fix: correct VirtualBox network configuration
chore: configure repository rules
\end{lstlisting}


\section{Repository Security and Sensitive Information}

The project repository is intended to be publicly accessible as part of
the project portfolio. For this reason, information stored in the
repository is classified according to its security impact.

The repository may contain technical information required to understand
the architecture, including:

\begin{itemize}
    \item private laboratory IPv4 addresses,
    \item laboratory subnet definitions,
    \item service port numbers,
    \item network topology,
    \item operating system and software information,
    \item cryptographic algorithms and protocols,
    \item infrastructure configuration examples.
\end{itemize}

Private IPv4 addresses used by the isolated laboratory environment, such
as addresses belonging to RFC1918 private address ranges, are considered
acceptable for the public documentation.

For example, the laboratory network:

\begin{center}
    \texttt{192.168.100.0/24}
\end{center}

may be documented because it is not globally routable and does not
directly expose the infrastructure to the Internet.


\subsection{Information Excluded from the Repository}

Information that could expose credentials, authentication material,
public infrastructure endpoints, or unnecessary host identifiers must
not be committed.

This includes:

\begin{itemize}
    \item passwords,
    \item API keys,
    \item access tokens,
    \item GitHub Personal Access Tokens,
    \item private SSH keys,
    \item database credentials,
    \item connection strings containing credentials,
    \item environment files containing secrets,
    \item public IP addresses of the physical infrastructure,
    \item unnecessary hardware or virtual interface identifiers,
    \item other credentials or authentication secrets.
\end{itemize}

Files commonly containing sensitive information are excluded using
\texttt{.gitignore} where appropriate.

Examples include:

\begin{lstlisting}[style=terminal]
.env
.env.*
*.key
*.pem
\end{lstlisting}

The \texttt{.gitignore} file is considered an additional protection
mechanism and must not be treated as the primary security control.

Sensitive information must never be placed inside the repository in the
first place.


\subsection{SSH Key Material}

SSH authentication is based on asymmetric cryptography.

The project documentation may describe the key algorithm used by the
environment, for example:

\begin{lstlisting}[style=terminal]
SSH key algorithm: ED25519
\end{lstlisting}

The cryptographic algorithm itself is not considered confidential
information.

Private SSH keys must never be committed to the repository.

The public component of an SSH key is not considered secret. However,
actual public keys are not included in the repository unless they are
required for a specific infrastructure configuration.

The documentation therefore describes the authentication mechanism
without unnecessarily publishing individual key material.


\subsection{SSH Host Fingerprints}

SSH host fingerprints are used to verify the identity of remote SSH
servers.

The documentation describes the verification procedure using commands
such as:

\begin{lstlisting}[style=terminal]
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
\end{lstlisting}

Actual fingerprints of laboratory machines are not required in the
public documentation.

When examples require a fingerprint, a placeholder should be used:

\begin{lstlisting}[style=terminal]
SHA256:<REDACTED>
\end{lstlisting}


\subsection{MAC Addresses}

MAC addresses are required during some Layer 2 network verification
procedures.

For example:

\begin{lstlisting}[style=terminal]
ip link show enp0s8
ip neigh show
\end{lstlisting}

and on Windows:

\begin{lstlisting}[style=terminal]
arp -a
\end{lstlisting}

The documentation describes how MAC addresses are compared during
network verification.

Actual interface MAC addresses are not recorded unless they are required
for a specific reproducible configuration.

Documentation examples should use placeholders such as:

\begin{lstlisting}[style=terminal]
<MAC_ADDRESS>
\end{lstlisting}


\subsection{Public Network Information}

Publicly routable addresses associated with the physical homelab
infrastructure must not be included in the public repository.

Documentation requiring such an address should use a placeholder:

\begin{lstlisting}[style=terminal]
<PUBLIC_IP>
\end{lstlisting}

Alternatively, IP address ranges reserved specifically for documentation
may be used in examples.

The same principle applies to public hostnames, Dynamic DNS addresses,
VPN endpoints, and other information that could identify an externally
reachable entry point into the infrastructure.


\subsection{Documentation Sanitization Policy}

Before changes are merged into the \texttt{main} branch, documentation
must be reviewed for information that should not become publicly
available.

The documentation sanitization process follows the principle:

\begin{center}
\textit{Document the architecture and mechanisms without unnecessarily
exposing the identity or access details of the real infrastructure.}
\end{center}

Sensitive or unnecessary operational values should be replaced with
descriptive placeholders.

Examples include:

\begin{tabular}{ll}

\section{Main Branch Protection}

The \texttt{main} branch is treated as the stable integration branch
of the project.

A GitHub repository ruleset is used to protect it from accidental or
uncontrolled modifications.

The repository policy includes:

\begin{itemize}
    \item changes to \texttt{main} should be introduced through
    Pull Requests,
    \item force pushes to \texttt{main} are prohibited,
    \item deletion of \texttt{main} is prohibited,
    \item Pull Request conversations should be resolved before merging,
    \item development is performed on dedicated branches.
\end{itemize}

At the current single-developer stage, an external Pull Request approval
is not required.

Once additional collaborators are introduced, the repository policy is
planned to require at least one approval before a Pull Request can be
merged into \texttt{main}.


\section{Merge Strategy}

The repository is intended to maintain a readable history on the
\texttt{main} branch.

Development branches may contain multiple intermediate commits while a
feature is being implemented.

Pull Requests can therefore be integrated using a squash-based strategy,
resulting in a single logical commit being introduced into
\texttt{main}.

Conceptually:

\begin{lstlisting}[style=terminal]
feature branch:

o---o---o---o
             \
              \  Squash Merge
               \
main: o---------O
\end{lstlisting}

This approach allows frequent commits during development while keeping
the primary branch history concise.


\section{Issues and Work Tracking}

GitHub Issues are used to represent individual tasks, bugs, documentation
work, and planned features.

A typical issue should define:

\begin{itemize}
    \item the objective of the change,
    \item the reason for implementing it,
    \item acceptance criteria,
    \item relevant technical considerations,
    \item verification requirements.
\end{itemize}

Development branches may reference the associated issue number.

For example:

\begin{lstlisting}[style=terminal]
feature/12-lab-network
\end{lstlisting}

Pull Requests can automatically close associated issues by including a
reference such as:

\begin{lstlisting}[style=terminal]
Closes #12
\end{lstlisting}


\section{Milestones}

GitHub Milestones are used to group Issues and Pull Requests belonging
to a larger project objective.

A milestone represents a significant stage of the homelab development
rather than an individual technical task.

The first milestone is defined as:

\begin{center}
    \texttt{M1 - Lab Foundation}
\end{center}

Its objective is to establish the initial technical foundation required
for further development.

The milestone includes areas such as:

\begin{itemize}
    \item virtualization,
    \item Ubuntu installation and configuration,
    \item basic networking,
    \item version control,
    \item remote administration,
    \item project documentation.
\end{itemize}

Progress of the milestone can be calculated from the completion state of
its associated Issues and Pull Requests.


\section{GitHub Project}

A GitHub Project is used as a higher-level work management tool.

While Milestones describe major objectives, the Project provides a view
of the current state of individual work items.

The project board is named:

\begin{center}
    \texttt{Homelab Infrastructure Roadmap}
\end{center}

The planned workflow consists of the following states:

\begin{lstlisting}[style=terminal]
Backlog
   |
   v
Ready
   |
   v
In Progress
   |
   v
In Review
   |
   v
Done
\end{lstlisting}

Issues and Pull Requests can be associated with the project and moved
between states as implementation progresses.

\section{Planned Improvements}

The repository configuration will evolve together with the project.

Planned improvements include:

\begin{itemize}
    \item mandatory Pull Request approvals after introducing additional
    collaborators,
    \item CODEOWNERS configuration,
    \item Pull Request templates,
    \item Issue templates,
    \item automated Continuous Integration checks,
    \item automatic LaTeX documentation compilation,
    \item dependency and security scanning,
    \item automated validation of infrastructure configuration,
    \item repository security policies.
\end{itemize}

These mechanisms will be introduced incrementally as the project grows,
rather than enabling unnecessary controls before they provide practical
value.
